# OneTrans-S 在昇腾 950DT 的训练性能复核报告 v4

- 日期：2026-11-17（v4：新增第七步「显式 bf16 干路」+ **TOP-DOWN 分阶段诊断** + 四项否决留证 + 剩余空间三档）
- 目标：按论文 arXiv:2510.26104 的 OneTrans-S 形状（91 M 参数、d=256、H=4、seq 1190→12、6 层 pyramid、per-GPU batch 2048）在
  **16 卡 950DT（2×8 die，122 + 111）** 上跑起来，实测步时/吞吐/MFU/显存，与论文 16×H100 的 407 ms **并列**对比（只做训练，不含推理）
- 目标判据（2026-11-17 用户设定）：**性能与 H100 持平 ⇒ 稳态 ≤ 427 ms**（407 × 1.05）
- 代码与原始数据：`github.com/xiaomingyao/OneTrans-S`（`main`，含 `results/prof16_o1_*.csv` 等全部 profile 原始件）

## 1 结论摘要

| 档 | 对齐轴 | 步时 | 全局 sps | 每卡 sps | MFU | HBM | vs 论文 407 ms | 距 427 ms |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| **A** 每卡 2048 + 激活重算 | 全局 batch **和** per-GPU batch 都对齐 | **752.0 ms** | 43,575.4 | 2,723.5 | **19.88%** | **39.17 GB** | 1.85× | 还需 −43.2% |
| **B** 每卡 1024×累加2、无重算 | 只对齐全局 batch 32,768 / 16 卡 | **614.7 ms** | 53,307.4 | 3,331.7 | **24.32%** | 58.48 GB | 1.51× | 还需 −30.5% |

相对起点（1,942.1 ms / 16,872.3 sps / MFU 7.70% / 52.30 GB）：
档 A **−61.28%** 步时、**+158.26%** 吞吐；档 B **−68.35%** 步时、**+215.95%** 吞吐。

**七步有效优化**：ns-layout → 融合 rms_norm → 去 cat（档 A/B 分档）→ SDPA 内置 causal → FA `BSH` → 全量投影 → **显式 bf16 干路**。
另有 **16 项实测无效 / 不可用**，全部留档（§4），避免重复投入。

**一句话诊断**：当前是**纯计算受限**（计算 98.6%、通信暴露 0.8%、气泡 0.7%），
cube 侧 348.4 ms 的平均效率只有 **50.9%**（FA 反向 35% 最差），向量侧 ~240 ms 是 memory-bound 的小算子海。
**不碰算法与数值精度的天花板是 493 ms（MFU 30.3%），到不了 427 ms。**

## 2 口径纪律（先读这段，否则数字会被误读）

1. **不与论文相除算「收益%」**：论文 407 ms 是 fp32 未优化基线，本仓是 bf16 + FA 融合 + 融合 norm + 显式 bf16 干路；只能并列。
2. **档 B 的 per-GPU micro-batch 是 1024×2**，论文是 2048 ⇒ 档 B 只在「全局 batch / 卡数」这一轴上对齐，**不可与档 A 混读**。
3. 档 A 与档 B 的数学目标相同（micro-batch 均值 ÷ 累加数 = 整批均值），但 bf16 重排 + AdamW 非线性会让 loss 轨迹分叉
   ⇒ **不可逐值比对、不可当精度回归**。
4. **精度记账分两级，不能混谈**：
   - **布局类（L1）**：`cat_inplace` / 全量投影 / FA `BSH` / SDPA causal —— 写入的值不变，只改地址与分块 ⇒
     logits 逐位或 `max|Δg|` ≤ **1 个 bf16 ULP**；可用于性能档，**不可当精度基线**。
   - **数值档变更（L2）**：**显式 bf16 干路（§3.7）** —— 干路逐元素运算从 fp32 降到 bf16，
     `mean rel|Δg| = 6.1e-3（0.61%）`、`worst rel 3.2%` ⇒ **是训练精度档的变更，不是噪声级微调**，单独记账。
5. 训练数据是合成 token 常驻 device，步时**不含取数/H2D**（纯计算口径）。
6. **跨节点实验必须先 md5 校验两节点代码一致**（踩过：只推一个节点 ⇒ rank0 跑旧码，收益被误判为 0，见 §3.8）。

## 3 优化逐项（七步有效）

### 3.1 ns-layout：NS-token 专有 QKV/FFN 由「逐 token Linear」合成一次 bmm

- 开关 `ONETRANS_NS_BMM=1`；CPU UT：参数量 471,938 一致、前向 `max|Δout| 5.96e-08`、反向 `worst rel|Δg| 1.34e-06` ⇒ 等价通过。
- 实测（16 die）：**1,942.0 → 1,442.9 ms（−25.70%）**，MFU 7.70% → 10.36%。

### 3.2 融合 rms_norm：手写 norm 链换成 `torch_npu.npu_rms_norm`

- 动机：手写链（`float→pow→mean→rsqrt→mul→改dtype→乘 fp32 weight`）实际占 **≈280 ms/步（19%）**，`Mul` 单项 151.6 ms。
- 开关 `ONETRANS_FUSED_NORM=1`；精度对 fp64 参考反而更好（`max_rel 3.891e-03` vs 手写链 `7.704e-03`）。
- 实测：**1,443.9 → 1,228.6 ms（−14.90%）**，MFU 10.35% → 12.17%，HBM 52.27 → 47.57 GB。

### 3.3 去 cat：`_project_one` 的 seq/ns 合并改「预分配 + 原地写」

- 开关 `ONETRANS_CAT_INPLACE=1`；逐算子：`Cat_ConcatD 51.4→7.8`、`InplaceCopy_Cast 143.1→78.5`、`InplaceCopy_Transpose 76.6→26.6`。
- 实测：档 A **1,228.6 → 1,112.1 ms（−9.48%）**；档 B **959.2 → 892.5 ms（−6.95%）**。

### 3.4 SDPA 内置 causal（`ONETRANS_SDPA_CAUSAL=1`）

- 事实：`paper_causal` 是**底右对齐**；SDPA 的 `is_causal=True` 在 `q≠k` 时是**左上对齐**（`max|Δ| 4.26`，不等价），
  但 `q_len == key_len` 的层两者是同一张掩码（base block + 第一个 pyramid block）。
- 精度：模型 logits **逐位相同（0.0）**。实测：档 A **−5.27%**、档 B **−5.06%**。

### 3.5 FA `BSH` 布局（`ONETRANS_FA_BSH=1`）

- 单算子 fwd（B512·H4·480×1203）**2.215 → 1.513 ms（−31.7%）**；16 die 档 B **847.3 → 823.5 ms（−2.81%）**。
- 精度：单算子前向逐位、`dk/dv` 逐位、`dq` 1 ULP；模型 2 步 `max|Δg| 2.44e-4`（0.5 ULP）。
- 两个坑：① **`atten_mask` 语义是「True = 屏蔽」**（与 SDPA 相反），传反**不报错但结果全错**（`max|Δ| 4.53`）；
  ② `Lq == ns_len` 的 12 行层 q 是 fp32 且非连续 ⇒ FA 报 `161002`，该分支限定 `ns_len < Lq < Lk and q.is_contiguous() and dtype 一致`。

### 3.6 全量投影 + 原地覆盖 NS 行（`ONETRANS_FULL_PROJ=1`）

- 改成**全量**投影（NS 的 12 行也走共享权重），再把 NS 行整块覆盖成独立权重结果 ⇒ 省一次整块 alloc + 一次全量写，
  代价是多算 `12/L ≈ 1%` 投影算力。
- 单 die batch 1024 **421.2 → 374.9 ms（−11.0%）**；16 die 档 B **847.3 → 753.0 ms（−11.13%）**。
- 精度：loss rel ≤ 9e-5；`max|Δg| 4.88e-4` = 最大梯度元素（0.154）的 **1 个 bf16 ULP**。

### 3.7 显式 bf16 干路（`ONETRANS_EXPLICIT_BF16=1`）—— 本轮最大的一步，**改变训练精度档**

- 做法：**关掉 autocast**，残差流/激活/权重全走 bf16（RMSNorm 输出与 block 入口强制 bf16，NS 的 fp32 bias 落 bf16），
  权重用每步一次的 bf16 影子（图仍接在 fp32 参数上，优化器仍算 fp32），只有 loss 前把 logits 转回 fp32。
- 目的：消灭 autocast 在「bf16 matmul ↔ fp32 逐元素」之间反复插入的激活 cast（16 die 上约 58 ms/步 + 大量 LayoutCopy）。

| 场景 | baseline | 显式 bf16 | Δ |
|---|---:|---:|---:|
| 单 die · batch 1024 | 363.5 ms | **305.1 ms** | −16.1% |
| 16 die · 档 B | 730.0 ms | **614.7 ms** | **−15.79%** |
| 16 die · 档 A | 895.3 ms | **752.0 ms** | **−16.01%** |
| HBM（档 B / 档 A） | 69.60 / 47.85 GB | **58.48 / 39.17 GB** | −11.1 / −8.7 GB |

- **精度（单 die、batch 256、1 步、同一初始权重、81 参数全梯度）**：loss rel **9.8e-5**；`max|Δg|` **5.33e-4**；
  `mean rel|Δg|`（`|g|≥1e-2`，173 个元素）**6.1e-3（0.61%）**；worst rel 3.25e-2；无 NaN/Inf。
  10 步 loss 轨迹两模式都稳定无发散。⇒ **精度档变更（L2），不可当基线**，默认关。
- 两个坑：① 该模式下 NS 路径的 fp32 bias 会把 q 提成 fp32，与 bf16 k/v 一起喂 SDPA 直接报 dtype 不一致 ⇒ NS bias 一起落 bf16；
  ② **权重影子缓存必须每步清**（漏清 ⇒ 第 2 步用陈旧权重，梯度 absmax 掉到 1/4，差点误判成"bf16 训练坏了"）。

### 3.8 累计成绩与一次自我纠错

| 配置（16 die · n=8） | 档 B 步时 | 档 A 步时 | 档 B MFU | 档 A MFU |
|---|---:|---:|---:|---:|
| baseline（仅 SDPA causal） | 847.3 ms | 1,053.5 ms | 17.64% | 14.19% |
| +FA BSH | 823.5 ms（−2.81%） | — | 18.15% | — |
| +全量投影 | 753.0 ms（−11.13%） | — | 19.85% | — |
| +两者同开 | 730.0 ms（−13.84%） | 895.3 ms（−15.02%） | 20.48% | 16.70% |

**自我纠错（必须记录）**：FA BSH 与全量投影**第一次测 16 卡时都得出「0.00%，无效」**，并据此写下"16 卡墙钟不由这些 kernel 决定"。
真因是 **rank0（122）的 `main_pytorch.py` 没有同步**（只推给 111）⇒ 那次测量作废、结论撤回。**纪律：跨节点实验开跑前 md5 双校验。**

修正后才是「慢 2.3~3.1×」；② RMSNorm 探针报「反向 −49%」来自 A 臂里 `x.detach().clone()` 的 602 MiB 拷贝开销，
真模型里没有这个拷贝。

## 5 TOP-DOWN 分阶段诊断（当前最优配置 · 16 die · 档 B · 3 稳态步）

**方法学（必读）**：先用 `record_function` 标记 + "kernel 落在谁区间内"做归属，结果**是错的**（`P_loss` 被算成 337 ms）——
CPU 标记是**入队窗口**，设备 kernel 要到 `loss.item()` 同步时才真执行，两条时间轴不对齐。
改用**差分法**（全步 profile − `--no-backward` profile）才得到下面的可信数字。

### 5.1 第一层：步时总账（官方 `step_trace_time`，3 步均值）

|---|---:|---:|
| **Stage（步时）** | **614.27** | 100% |
| Computing（设备计算） | **605.47** | **98.6%** |
| Communication（AllReduce） | 19.47 | 3.2% |
| ├─ 被计算掩盖 | 14.80 | — |

### 5.5 利用率（按各自 FLOP 公式，分母 432 TF/s）

| 部分 | 时间 | FLOPs/卡/步 | 实测 | 效率 |
|---|---:|---:|---:|---:|
| FA 前向 | 41.0 ms | 7.94 TFLOP | **193.8 TF/s** | **44.8%** |
| FA 反向 | 131.3 ms | 19.86 TFLOP（2.5×） | **151.3 TF/s** | **35.0%** |
| GEMM（前 + 反） | 176.1 ms | 16.30 × 3 = **48.9 TFLOP** | **277.6 TF/s** | **64.3%** |
| **cube 合计** | **348.4 ms（54.8%）** | **76.7 TFLOP** | **220.1 TF/s** | **50.9%** |
| 整步（记账口径 64.57 TFLOP） | 614.3 ms | 64.57 TFLOP | 105.1 TF/s | **24.33%（MFU）** |

**自纠**：v4 草稿曾把 GEMM 写成 21.4% —— 分母只算了**前向** FLOPs，而线性层反向是 2× 前向。正确是 **64.3%**，
因此 GEMM **不是**瓶颈，瓶颈排序改为：向量侧 240 ms > FA 反向 131 ms（35%）> GEMM。

向量侧带宽实测（1024×1203×256 bf16，单张量 602 MiB）：SiLU **3178 GB/s**、Add **3222 GB/s**（均已贴 HBM 上限）、
`npu_rms_norm` **1445 GB/s（峰值 45%）**、手写 rmsnorm 319 GB/s。

## 6 与论文 16×H100 并列对比

| 项 | 论文 OneTrans-S（16×H100） | 本仓 950DT 档 A | 本仓 950DT 档 B |
|---|---:|---:|---:|
| 稳态步时 | **407 ms** | **752.0 ms** | **614.7 ms** |
| 全局吞吐 | 80,511 sps（**推算**，论文未给） | 43,575.4 sps | **53,307.4 sps** |
| 每卡吞吐 | 5,032 sps（2048 ÷ 0.407 s，**推算**） | 2,723.5 sps | 3,331.7 sps |
| MFU | **S 未给**（OneTransL 30.8% bf16、DCNv2+DIN 13.4%） | **19.88%** | **24.32%** |
| 显存 | 53.13 GB（fp32 未优化档） | **39.17 GB** | 58.48 GB |
| 口径 | fp32、未优化基线 | bf16 + FA v4 + 融合 norm + 显式 bf16 干路 | 同左，per-GPU batch 1024×2 |

**并列读数**：档 A 是 **1.85×**、档 B 是 **1.51×**。这个比值只表示"同形状下两套栈的稳态步时之比"，
**不是**"昇腾比 H100 慢 N 倍"——口径不同，按 §2.1 不得相除求收益。

## 7 剩余空间（按"可动性"分三档）

| 档 | 项 | 预估 | 前提 / 阻塞 |
|---|---|---:|---|
| **一（确定性）** | `ReduceSum 20.8 ms / 158 次` 定位并消除 | **−20** | 至今未定位（Python 层每步只发 1 次 `mean`） |
| | `Zero 14.0 ms / 580 次` | −14 | autograd 的 `zeros_like`；参数按组拆 + 自定义反向 |
| | 搬运/重排残余（`TensorMove 26.0`、`Transpose 11.6`） | −15 | G3 已吃大头，剩 NS 路径与 narrow |
| | NS 12 行小 GEMM 合并（210 次 × 18 µs） | −3.8 | 已验证逐位相同 |
| | add+norm 融合（intra-block 14 对） | −4.3 | `npu_add_rms_norm` 已验证 |
| | 图模式消 launch | −4.1 | 就是气泡上限 |
| | 通信暴露部分 | −4.7 | — |
| | **小计** | **≈ −67** | ⇒ **548 ms（MFU 27.3%）** |
| **二（cube 效率）** | FA 反向 35% → 45%（追平前向） | −29 | API 旋钮全灭、Triton 自写更慢 |
| | GEMM 64.3% → 75% | −25 | 形状天生小（M=12/256, N=256） |
| | **小计** | **≈ −54** | ⇒ **493 ms（MFU 30.3%）** |
| **三（要决策）** | 自定义反向（压反向那 ~195 ms 向量算子海） | **−90** | 等于重写全部 backward |
| | FP8 训练 | cube 理论 ×2 | 需 scale recipe，精度风险最高 |
| | 减算力（K/V 剪枝 / 更激进 pyramid / ns_len） | 每 −10% 算力 ≈ −35 ms | **与论文结构冲突（已冻结）** |
| | 档 A 专项：分块重算 | 档 A 752 → ~700 | 只改善论文口径那一列 |

**结论**：不碰算法与数值精度，天花板 **493 ms（MFU 30.3%）**，**到不了 427 ms**。
要「持平 H100」，只能在**自定义反向**或 **FP8 / 减算力**上做一次大改；零碎优化凑不出来。

## 8 未闭合项（明确未做/未定，不含推测）

1. **论文 Table 3 的 pyramid 算术倍率口径**：本仓 pyramid 开/关实测 **1.68×**，论文表格口径 3.06×；
   按论文正文写法（只剪 query、K/V 为层输入全序列）计算为 **1.66×**，与实测自洽 ⇒ 判为**论文表格口径待核**，不为它改码。
2. **`ReduceSum 20.8 ms / 158 次`** 与 **`Zero 14.0 ms / 580 次`** 的来源：全仓无 `clip_grad_norm_`、无 `.sum(` 调用，
   `probe_op_callers` 证明 Python 层每步只发 14 次 `to`、6 次 `narrow` ⇒ 归因未定位，不作结论。
3. **图模式**：手动 capture 已确认被 attention 算子内部的旁路 stream 封死；TorchAir 卡在"我们的投影/掩码写法对图编译器不友好"
   （`k-axis 1191`），要吃 GE 融合需先做 trace 友好化改造，未排期。
4. 每卡 batch 4096、"每卡 2048 去掉重算"两条路均被显存/算子封死（E5、`FlashAttentionScoreGradV4` 失败）。
5. **`npu_add_rms_norm` 的训练可用性**：前向已验证（−33%、h 逐位相同），但反向必须自写 kernel，未实施。
6. profiler 在 torch_npu 2.10 上导出的 `Call Stack` 列**恒为空**（`--profile-with-stack` 不生效）⇒ 归因只能靠
   TorchFunctionMode / CPU profiler shape / 差分法。
