# Triton 融合 MixedMHA 方案评估（理论 + 一次作废的实测）

- 日期：2026-11-17
- 提出：用 Triton 把 `QK^T → Causal Mask → Softmax → PV` 融进一个 kernel，让中间结果留在片上，避免 HBM 回写
- 结论：**理论收益上限 0.6% 步时；实测三次均不可用**（本次实测因环境问题作废，前两次为「慢 2.3~3.1×」）
- 与 `aclnnFlashAttentionScoreV4`（下称 FA v4）的关系：**替代关系，不是互补**；两者可共存但不该共存

## 1 前提核对：本仓已经在用融合 attention

「融合以免 S² 回写 HBM」这个论证的对象是 **naive PyTorch 拼装**。本仓不是 naive：

| 实现 | S² 分数矩阵 HBM 流量 | 折合时间 |
|---|---:|---:|
| naive（`matmul → masked_fill → softmax → matmul`） | 7 个 block 合计 85.8 GB/次；写+读两遍 **172 GB** | **≈54 ms** |
| **本仓（FA v4，每步 14 次调用）** | **0** | 0 |

## 2 理论账：attention 在这个形状下是**算力受限**，融合省不到时间

单 micro-batch、B=1024、H=4、D=64（BH=4096）、底右因果：

| block | Lq | Lk | TFLOP | GB | 算术强度(FLOP/B) | 算力下界 | 带宽下界 | 受限 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| base / stack0 | 1203 | 1203 | 1.518 | 2.52 | 601 | 3.51 ms | 0.79 ms | 算力 |
| stack1 | 960 | 1203 | 1.211 | 2.27 | 534 | 2.80 | 0.71 | 算力 |
| stack2 | 736 | 960 | 0.741 | 1.78 | 417 | 1.72 | 0.56 | 算力 |
| stack3 | 480 | 736 | 0.370 | 1.28 | 291 | 0.86 | 0.40 | 算力 |
| stack4 | 256 | 480 | 0.129 | 0.77 | 167 | 0.30 | 0.24 | 算力 |
| **stack5（NS 12 行）** | 12 | 256 | 0.003 | 0.28 | 12 | 0.007 | 0.088 | **带宽** |
| **合计** | | | **5.489** | **11.42** | **481** | **12.71 ms** | **3.57 ms** | |

- 算术强度 481 ≫ Ascend 机器平衡点（≈110）⇒ **纯算力受限**。
- **即便把 attention 的 HBM 流量降到 0，每步最多省 3.57 ms = 步时的 0.6%**。这是该方向的绝对上限。
- 唯一的带宽受限层是 stack5（Lq=12），但它总共只有 0.28 GB / 0.088 ms ⇒ 全压掉 ≈ **0.1 ms/步**。

口径说明：FA 实测 20.5 ms/micro-batch；按整矩形口径是 62% 峰值，按因果半三角口径是 31%。
仓里记录的前向 44.8% 属另一套（64.57 TFLOP 总记账）分摊口径，**三者不可互比**，本节统一用整矩形口径。

## 3 即便 Triton 写得完美，也赢不了 FA v4：三条结构性原因

1. **Ascend 的 FA 依赖 cube/vector 双单元流水**：QK^T 在 cube，P 搬 UB，softmax 在 vector，P 回 L1，PV 在 cube。
   厂商是手写 AscendC + L1/L0C/UB 三级显式 staging（双缓冲）。Triton 只能表达 `tl.dot` + 逐元素，
   编译器把两段**串行**掉 —— 这不是调参能解决的，历史两次实测就是 **3.08×** 与 **2.32×**（前向，best tile）。
2. **cube∥vector 并发实测只有 15% 重叠效率**（`probe_stream_overlap.py`：串行 2.192 → 并发 2.102 ms，理想 1.604），
   一旦被串行化，损失无法靠调度补回。
3. **FA 反向是融合核**：`FlashAttentionScoreGradV4` 一次算完 dq/dk/dv，131.3 ms/步（占步时 21%）。
   自写要做三遍 + 重算，等于把 131 ms 放大到 400 ms 量级。

## 4 与 FA v4 是否冲突

| 维度 | 判断 |
|---|---|
| 算子共存 | **不冲突**：可按 dtype/shape 路由并存，与 DDP、图模式、ckpt 无关 |
| 功能 | **重叠**：FA v4 已做同一套融合，且带反向；Triton 版无反向 |
| 性能 | **冲突（更差）**：前向实测慢 2.3~3.1× |
| 语义 | **必须严格对齐**：FA 的 `atten_mask` 是 **True=屏蔽**（与 SDPA 相反）；底右因果是 `col ≤ row + (Lk−Lq)`；本项目曾因 `n_start` 写反跑出「快 29%/51%」的假加速 |
| 边界 | FA 在 `Lq == ns_len`（12 行）且 q 非连续时报 `161002`，本仓用分支绕开；自写版要重新处理该 case |

**结论：不是互补，是替代；而且替代品更慢、缺反向。**

## 5 attention 附近真正还剩的字节机会（都不需要重写 attention 主体）

| 机会 | 规模 | 上限 |
|---|---:|---:|
| **PV 输出 + out-proj + 残差 + rms 一次过**（尾部融合） | 0.63 GB/层 ×14 | **≈2.8 ms（0.5%）** |
| stack5 的 12 行走小 matmul、不过 FA | 0.28 GB | ≈0.1 ms |
| NS 12 token 的 bmm 路径消掉（与 FA 无关，属搬运家族 46.3 ms） | — | 数 ms |

## 6 实测：本轮（`probe_triton_mixed_mha.py`）**作废**，证据如下

跑了 7 个真实形状 + 15 组块尺寸，输出全部是：

```
[triton 0.058~0.081 ms] [FA 0.169~0.190 ms] [triton/FA 0.33~0.48x]
[有效带宽 3 454~43 125 GB/s]  max|Δ| 0.000e+00  mean 0.000e+00
```

**这些数字物理上不可能**：
- FA 在 `BH=4096, Lq=Lk=1203, D=64` 上是 1.518 TFLOP ⇒ 0.180 ms 意味着 **≈8 400 TF/s**（峰值 432）。
  参考：同形状 `BH=1024` 的历史实测是 7.47 ms。
- 0.06 ms 的 Triton 时间 = 纯下发开销；bandwidth 判据（>4000 GB/s 即 INVALID）把所有 case 都标了出来。
- 第一个 case（base）直接 `RuntimeError: The Inner error ...`，**此后所有 case 都是 0.06 ms** ⇒ 首个失败后设备/上下文进入异常态，
  后续 kernel 全部没有真正执行；`max|Δ| = 0.000e+00` 是"两边都是未写入的同一缓冲"造成的假象。

**两条方法学教训（已写进判据）**：
1. 带宽判据只保护了 Triton 侧，**FA 侧也要有算力下界判据**（本次就是 FA 侧的数字先暴露了问题）。
2. 一个形状失败会污染后续所有测量 ⇒ **每个形状必须独立进程**（与 §8 图模式二分同样的做法）。

若要拿到干净数据，需重跑：`--only <idx>` 逐形状独立进程 + 双侧下界断言（Triton ≥ 带宽下界×0.5，FA ≥ 算力下界×0.5）。
但按 §2 的理论账，重跑的意义只是"证明与 FA 相当"，**上限仍是 0.6%**，不建议投入。
