MFU 口径（2026-11-17 自纠）：FlopCounterMode 不数 attention（实测 SDPA=0、npu_fusion_attention=0，只数 Linear/mm）， 所以"只算 Linear/mm"的 31.53 GFLOP/sample 只是下界。含 attention（因果半三角）后 = 40.91 GFLOP/sample ⇒ 83.8 TFLOP/卡/步， MFU 主口径 31.6% / 25.8%（上界——attention 按全矩形计——是 38.8% / 31.7%）。三档口径并列，不混用。

一句话诊断：纯计算受限 —— 计算占 98.6%、通信暴露 0.8%、气泡 0.7%； cube 348.4 ms 平均效率 50.9%（FA 反向 35.0% 最差、GEMM 64.3%），vector 侧 ~240 ms 已贴 HBM 峰值（SiLU 3178 / Add 3222 GB/s）， 且 cube∥vector 无法重叠（双流重叠效率仅 15%）。

结论（必须直说）：

  1. 287 ms 在"现行算法 + 可用算子"下不可达——硬约束：vector 240 ms + FA 跑满 bf16 峰值的 64 ms = 304 ms > 287 ms， 而注意力没有任何量化入口（§5 Q2）。
  2. 即使 cube 跑到 100% 峰值、vector 停在 240 ms，步时也是 426 ms = 273 ms 的 1.56×； 硬件上 950DT 的 bf16 峰值只有 H100 的 43.7%（§3）。
  3. 现实可达区间：561（A）→ 531（A+C）→ 470（A+C+int8）→ 408（再加减算力），见 §8。

2 口径纪律（先读这段，否则数字会被误读）

判据三档（2026-11-17）：论文 Table 4 是单点消融表（四行百分比都相对 407 ms：290/407=−28.7%、284/407=−30.2%、 203/407=−50.1%、273/407=−32.9%，且 203→273 不单调）。主判据取 273 ms 那一行（bf16 + 激活重算 = 与本仓档 A 同精度档）， 407 ms（fp32 未优化）与 203 ms（+FA 单点最强）只作参考，不拿 fp32 基线当"持平"依据。

  1. 不与论文相除算「收益%」：论文 407 ms 是 fp32 未优化基线，本仓是 bf16 + FA 融合 + 融合 norm + 显式 bf16 干路；只能并列。
  2. 档 B 的 per-GPU micro-batch 是 1024×2，论文是 2048 ⇒ 档 B 只在「全局 batch / 卡数」这一轴上对齐，不可与档 A 混读。
  3. 档 A 与档 B 的数学目标相同（micro-batch 均值 ÷ 累加数 = 整批均值），但 bf16 重排 + AdamW 非线性会让 loss 轨迹分叉 ⇒ 不可逐值比对、不可当精度回归。
  4. 精度记账分两级，不能混谈： - 布局类（L1）：cat_inplace / 全量投影 / FA BSH / SDPA causal —— 写入的值不变，只改地址与分块 ⇒ logits 逐位或 max|Δg| ≤ 1 个 bf16 ULP；可用于性能档，不可当精度基线。 - 数值档变更（L2）：显式 bf16 干路（§3.7） —— 干路逐元素运算从 fp32 降到 bf16， mean rel|Δg| = 6.1e-3（0.61%）、worst rel 3.2% ⇒ 是训练精度档的变更，不是噪声级微调，单独记账。
  5. 训练数据是合成 token 常驻 device，步时不含取数/H2D（纯计算口径）。
  6. 跨节点实验必须先 md5 校验两节点代码一致（踩过：只推一个节点 ⇒ rank0 跑旧码，收益被误判为 0，见 §3.8）。

读法：算力只有 H100 的 44%，而带宽/容量基本持平（机器平衡点只有 H100 的 0.4×）。于是：

  • 凡 memory-bound 的部分（我们的 vector 侧 240 ms）两台机器打平，优化它不会缩小差距；
  • 凡 compute-bound 的部分（cube 348.4 ms）差距被双重放大：峰值低 2.29× × 效率只有 50.9%；
  • 这解释了为什么"论文的手段我们都做了（§9）"，结果仍差 2.6×：差的是同一套手段在低算力/高带宽机器上的执行效率。
  • 也解释了 287 ms 不可达的算术：H100 在 273 ms 内完成 83.8 TFLOP（主口径）需要 307 TF/s/卡（其峰值 989.4 的 31%）， 而我们即使达到 100% 峰值（432 TF/s）也要 194 ms 只是 cube，加上 240 ms 的 vector 就是 434 ms。

4 优化逐项（七步有效）

4.1 ns-layout：NS-token 专有 QKV/FFN 由「逐 token Linear」合成一次 bmm

  • 开关 ONETRANS_NS_BMM=1；CPU UT：参数量 471,938 一致、前向 max|Δout| 5.96e-08、反向 worst rel|Δg| 1.34e-06 ⇒ 等价通过。
  • 实测（16 die）：1,942.0 → 1,442.9 ms（−25.70%），MFU 7.70% → 10.36%。

4.2 融合 rms_norm：手写 norm 链换成 torch_npu.npu_rms_norm

  • 动机：手写链（float→pow→mean→rsqrt→mul→改dtype→乘 fp32 weight）实际占 ≈280 ms/步（19%），Mul 单项 151.6 ms。
  • 开关 ONETRANS_FUSED_NORM=1；精度对 fp64 参考反而更好（max_rel 3.891e-03 vs 手写链 7.704e-03）。
  • 实测：1,443.9 → 1,228.6 ms（−14.90%），MFU 10.35% → 12.17%，HBM 52.27 → 47.57 GB。

4.3 去 cat：_project_one 的 seq/ns 合并改「预分配 + 原地写」

  • 开关 ONETRANS_CAT_INPLACE=1；逐算子：Cat_ConcatD 51.4→7.8、InplaceCopy_Cast 143.1→78.5、InplaceCopy_Transpose 76.6→26.6。
  • 实测：档 A 1,228.6 → 1,112.1 ms（−9.48%）；档 B 959.2 → 892.5 ms（−6.95%）。

4.4 SDPA 内置 causal（ONETRANS_SDPA_CAUSAL=1）

  • 事实：paper_causal 是底右对齐；SDPA 的 is_causal=True 在 q≠k 时是左上对齐（max|Δ| 4.26，不等价）， 但 q_len == key_len 的层两者是同一张掩码（base block + 第一个 pyramid block）。
  • 精度：模型 logits 逐位相同（0.0）。实测：档 A −5.27%、档 B −5.06%。

4.5 FA BSH 布局（ONETRANS_FA_BSH=1）

  • 单算子 fwd（B512·H4·480×1203）2.215 → 1.513 ms（−31.7%）；16 die 档 B 847.3 → 823.5 ms（−2.81%）。
  • 精度：单算子前向逐位、dk/dv 逐位、dq 1 ULP；模型 2 步 max|Δg| 2.44e-4（0.5 ULP）。
  • 两个坑：① atten_mask 语义是「True = 屏蔽」（与 SDPA 相反），传反不报错但结果全错（max|Δ| 4.53）； ② Lq == ns_len 的 12 行层 q 是 fp32 且非连续 ⇒ FA 报 161002，该分支限定 ns_len < Lq < Lk and q.is_contiguous() and dtype 一致。

4.6 全量投影 + 原地覆盖 NS 行（ONETRANS_FULL_PROJ=1）

  • 改成全量投影（NS 的 12 行也走共享权重），再把 NS 行整块覆盖成独立权重结果 ⇒ 省一次整块 alloc + 一次全量写， 代价是多算 12/L ≈ 1% 投影算力。
  • 单 die batch 1024 421.2 → 374.9 ms（−11.0%）；16 die 档 B 847.3 → 753.0 ms（−11.13%）。
  • 精度：loss rel ≤ 9e-5；max|Δg| 4.88e-4 = 最大梯度元素（0.154）的 1 个 bf16 ULP。

4.7 显式 bf16 干路（ONETRANS_EXPLICIT_BF16=1）—— 本轮最大的一步，改变训练精度档

  • 做法：关掉 autocast，残差流/激活/权重全走 bf16（RMSNorm 输出与 block 入口强制 bf16，NS 的 fp32 bias 落 bf16）， 权重用每步一次的 bf16 影子（图仍接在 fp32 参数上，优化器仍算 fp32），只有 loss 前把 logits 转回 fp32。
  • 目的：消灭 autocast 在「bf16 matmul ↔ fp32 逐元素」之间反复插入的激活 cast（16 die 上约 58 ms/步 + 大量 LayoutCopy）。

6.6 三个新证据（2026-11-17，本报告新增）

  1. GEMM 在模型里只有 277 TF/s，而隔离同形状能到 376–427 TF/s（(1.23M,256)@(256,1024) = 403 TF/s，weight-grad 方向 (256,1.23M)@(1.23M,1024) = 425.7 TF/s）⇒ 不是形状问题，是串行/交织问题，上限约 −54 ms，是当前最大未挖掘项。
  2. cube∥vector 无法重叠：双流实测串行 2.192 ms → 并发 2.102 ms，理想下界 1.604 ms，重叠效率仅 15% （与 profile 里 kernel 时长之和 636.1 ms vs 并集 605.5 ms = 4.8% 一致）⇒ 步时 ≈ cube + vector 串行相加。
  3. ReduceSum 21.05 ms / 200 次 已归因：邻居链 SiluGrad → Mm → Mm → ReduceSum → Add → Cast(0.002) 证明它就是 F.linear 的 db = dy.sum(0)；隔离实测 contiguous bf16 (1.23M,1024) 的 sum(0) = 0.751 ms = 3358 GB/s（贴峰值）， 换 cube 的 ones@dy 仅 0.96×（无收益）；两条病态路径（sum(dtype=fp32) 653 GB/s、非连续 194 GB/s）不是当前主因。

10 未闭合项（明确未做/未定，不含推测）

  1. 论文 Table 3 的 pyramid 算术倍率口径：本仓 pyramid 开/关实测 1.68×，论文表格口径 3.06×； 按论文正文写法（只剪 query、K/V 为层输入全序列）计算为 1.66×，与实测自洽 ⇒ 判为论文表格口径待核，不为它改码。
  2. ReduceSum / Zero 的来源：ReduceSum 已归因为 F.linear 的 bias 梯度 db = dy.sum(0)（邻居链 SiluGrad → Mm → Mm → ReduceSum → Add → Cast，每步 200 次 / 21.05 ms，隔离实测已贴峰值，见 §7 自纠）；Zero（580 次 / 14.0 ms）确认为 zeros_like 紧跟 TensorMove/Slice 的 autograd slice/expand 反向，但具体发起点仍未逐条打点，不作结论。 probe_op_callers 证明 Python 层每步只发 14 次 to、6 次 narrow ⇒ 归因未定位，不作结论。
  3. 图模式：手动 capture 已确认被 attention 算子内部的旁路 stream 封死；TorchAir 卡在"我们的投影/掩码写法对图编译器不友好" （k-axis 1191），要吃 GE 融合需先做 trace 友好化改造，未排期。
  4. 每卡 batch 4096、"每卡 2048 去掉重算"两条路均被显存/算子封死（E5、FlashAttentionScoreGradV4 失败）。
  5. npu_add_rms_norm 的训练可用性：前向已验证（−33%、h 逐位相同），但反向必须自写 kernel，未实施。
  6. MFU 分子的口径：FlopCounterMode 不数 attention（已实测），现主口径 = Linear/mm + attention 因果半三角 = 40.91 GFLOP/sample； 若要把向量侧（SiLU/Add/Norm/ReduceSum）也计入"记账 FLOPs"，需要另立一套"算子级复算"口径，尚未做。
  7. 模型内 GEMM 为什么只有 277 TF/s（隔离 376–427）：形状已排除，待查三处——小 M 层（Lq=480/256/12）占比、 Addmm（带 bias）是否走更低效的 kernel、GEMM 前后的 ViewCopy/Transpose/TensorMove 与 NS 12 行的 210 次 BatchMatMul 是否打断流水。这是 §8 档 A 的入口。
  8. 950DT 容器可见 HBM 91.75 GiB 与标称 144 GB 的差异：未查（保留区/ECC/集群配置），不影响当前结论，但影响"能否开更大 micro-batch"的判断。
