模型结构对账：论文 vs 上游 GPU 参考 vs 本仓昇腾（2026-11-17）

对象：

  • 论文 papers/OneTrans_2510.26104v3.txt §4.1.4 / Table 2
  • 上游 GPU 参考 WestbrookLong/OneTrans_Pytorch（submodule GPU_Reference，commit 8febd7e）
  • 本仓 OneTrans_NPU/（main_pytorch.py + models/taac_onetrans.py）

0 结论

  1. 本仓与上游 GPU 参考：结构逐位等价（不是"大致相同"，是同一份定义 + 一层可关的 NPU 优化开关）。 证据：同一配置下 949 个张量、state_dict 的 key 集合与形状全等、前向输出 md5 完全相同、参数量同为 91,026,946、 pyramid schedule 同为 [1203, 960, 736, 480, 256, 12]。
  2. 本仓与论文：主干超参对齐，但有 4 处需要标注的差异/推定（见 §2 表的「⚠️」行）： 梯度裁剪缺失、优化器不同、FFN 宽度未知（以参数量反推）、「6 stacked blocks」与我们的 7 个 block 的表述歧义。
  3. 论文的 2.64 TFLOPs 无法与本仓对账，且该数字在论文自身口径下不自洽（见 §3）⇒ 只能当"论文自报"引用。

2.1 两个需要写进报告的口径说明

  1. 层数口径：论文正文说 "6 stacked OneTrans blocks"，但我们的实现是 base block + 6 个 pyramid block（上游亦如此）， 且只有在 ffn_hidden=1536 时参数量才刚好落到 91,026,946 ≈ 论文 91 M。 若论文的 6 是"总层数"，则我们的 block 数多 1、且 FFN 宽度需另调才能到 91 M —— 两个自由度互相补偿， 无法从论文文字唯一确定，故标注为推定，不声称"完全对齐"。
  2. 参数量口径：论文明确 "Params (model parameters excluding sparse embeddings)"；本仓是纯稠密实现（无稀疏表）， 两者同口径（都只数稠密参数），91 M 与 91,026,946 相差 0.03% ⇒ 构成可比的等价性证据（不是数值巧合）。

3 计算量对账（2.64 TFLOPs）

论文原文（§4.1.2 脚注段）："We report Params (model parameters excluding sparse embeddings) and TFLOPs (training compute in TFLOPs at batch size 2048)"。

读法论文本仓（主口径）倍数
每步（batch 2048，单卡）2.64 TFLOP83.8 TFLOP31.7×
每样本1.29 GFLOP40.91 GFLOP31.7×（同比例）
下界口径（本仓只算 Linear/mm）—64.6 TFLOP/步24.5×

但论文这一列自身不自洽：一次前向就要 2 × 91 M × 1190 = 216.6 GFLOP/sample， batch 2048 摊下来是 443 TFLOP，已经是 2.64 TFLOP 的 168 倍——还没算反向。 ⇒ 2.64 TFLOPs 不可能是"batch 2048 的训练计算量"，只能是某种归一化/笔误； 它的唯一可用之处是 Table 2 内部的相对比较（2.64T vs RankMixer+Transformer 2.51T）。

本仓的计算量是自洽的：91 M 参数里绝大部分是 13 组 NS/seq 分组的 QKV 与 FFN （序列 token 只用其中 1 组），所以每 token 的有效算力远低于"全部参数都作用到每个 token"的朴素估算： 40.91 GFLOP/sample ÷ 1203 token = 34.0 MFLOP/token。

4 待办

  2. 把 §2.1 的两条推定（层数口径、FFN 宽度）写进报告 v5 的"未闭合项"。
  3. （可选）把优化器换成论文的 RMSProp 做一次 loss 轨迹对照，验证收敛无系统性偏差。
